# 已知评测用例基线

> 更新时间：2026-09-04  
> 本文只整理目前已知的评测参数及其代表的能力覆盖面。当前仓库为公开仓库，因此不写入内部账号、工号、appid、Token、内部地址等不宜公开的信息。

## 1. 说明

当前已获得 10 条评测任务参数。它们用于验证不同 Agent Harness 在 Windows 办公环境中的实际任务完成能力。

这些任务**不是系统架构本身的功能列表**。本项目的核心仍然是：

- 自研统一 Agent 网关；
- 接入多个真实 Harness；
- 让不同 Harness 通过同一评测协议执行相同任务；
- 保持业务层和网关核心不依赖具体引擎。

尚未提供，因此下表的"输入"列记录的是 `query` 中写明的路径，不代表我们已持有这些文件。

### 2.1 任务书示例用例（不在这 10 条内）

任务书正文给出的示例是：

```json
{ "task_id": "office_002", "title": "打开Outlook客户端",
  "query": "请自动打开 Outlook 邮件客户端",
  "category": "办公协作、沟通与日程管理类", "secondary_category": "软件交互",
  "difficulty": 1, "difficulty_label": "极易" }
```

这条示例很重要：它说明**"软件交互"是一个独立的二级分类**，隐藏用例中很可能还有更多
"操作某个 Windows 桌面客户端"类任务。加上 `office_028` 的 WeLink 发消息，
**Windows GUI 自动化不是十条里只占一条的边缘能力，而是一个完整的任务类别**，
在能力注入的优先级上应与 Office 文件处理同级。

### 2.2 难度分布

| 难度 | 数量 | 说明 |
| --- | --- | --- |
| 1 极易 | 1（`office_028`） | 但依赖 GUI 自动化，实际失败风险不低 |
| 3 中 | 5 | 文档编辑/生成/转换、文件管理、信息检索 |
| 4 较难 | 3 | 全部是数据分析类，要求结构化长文本产出 |

难度标签衡量的是任务本身的认知复杂度，不代表工程实现难度。
`office_028` 标为"极易"，但它是十条里唯一强依赖桌面 GUI 的用例，
一旦网关以非交互式会话启动就会因 Windows Session 0 隔离而必然失败。

## 3. 各用例的验收要点

以下要点从 `query` 原文直接推导，用于我们自建的本地回归框架做程序化校验
（并非评测方的评分细则，评测方使用 LLM-as-Judge）。

| Task ID | 可程序化校验的点 |
| --- | --- |
| `office_011` | 目标 docx 存在且可被 python-docx 打开；章节结构与原文一致；GitHub Stars / MIT / 自托管 / 主流云厂商采用等关键信息仍在；仅"执行摘要"两段被改写 |
| `office_014` | md 文件存在；含高风险特征、低风险特征、≥3 条建议、一个按风险排序的样本表；数值与 `task.csv` 可对账（防幻觉） |
| `office_015` | md 文件存在；字数落在 500–800；覆盖 age/income/monthly_spend/debt_ratio 四字段的分层；包含分层口径与异常样本 |
| `office_018` | md 文件存在；分成高优先级补货 / 需要观察 / 库存相对安全三类；给出排序依据与建议动作 |
| `office_022` | pptx 存在且可被 python-pptx 打开；第 3–7 页仍在且数据点未丢失；页数与原文件一致 |
| `office_028` | 消息实际送达（需人工或客户端侧确认）；**幂等性**——重试不得重复发送 |
| `office_035` | `D:\test_data\openclaw.pptx` 存在；页数 ≤5；覆盖基本介绍/核心功能/核心架构/部署方式/部署依赖五个主题；**不得中途询问大纲** |
| `office_103` | 目标文件确已删除；**不含关键字的文件一个都没被误删**（这是最危险的用例） |
| `office_132` | 目标 xlsx 存在于 `D:/test_data_备份/`；sheet 数量等于源文档表格数量；每个 sheet 的行列数与源表一致 |
| `office_139` | 有实际检索行为（轨迹中可见联网工具调用）；结论带来源；具备时效性 |

### 3.1 两条高危用例

- **`office_103` 递归删除**：作用域控制错误会造成不可逆的数据破坏。网关的权限策略
  应对递归删除类命令保留审批钩子，即使评测配置为默认允许，也要在轨迹里留下完整记录。
- **`office_028` 外部消息**：唯一有外部副作用且不可撤销的用例。重试策略必须幂等，
  失败后盲目重试会造成重复发送。

**注意力分配的直接结论**：文件系统读写与结构化产物生成命中 7–8 条，
是投入产出比最高的能力；Office 三件套（docx/xlsx/pptx）各命中 2 条但合计 6 条；
GUI 自动化虽只命中 1 条，却因为示例用例和二级分类的存在而代表一整个隐藏类别。

## 5. 对 Harness 的直接要求

从这些样例可以观察到，效果较好的参赛 Harness 至少需要具备或能够通过 Tool / MCP / Skill 获得：

- 本地文件系统访问；
- Windows 命令/进程执行；
- Office 文件处理能力；
- Python / Node 等代码执行能力；
- 网页搜索或浏览能力；
- 必要时的 Windows Computer Use；
- 多步 Agent Loop；
- 工具调用结果继续进入后续推理；
- 任务结束前能够检查产物或环境状态。

这些能力可以由 Harness 原生提供，也可以由 PNP 通过统一资产层注入；核心原则是不把具体任务执行逻辑硬编码进网关。

## 6. 不应针对样例硬编码

实现中不应该依赖：

- `task_id == office_xxx`；
- 固定测试文件内容；
- 固定文件名判断后直接执行预设答案；
- 固定联系人账号；
- 任何未知隐藏数据集的猜测。

网关负责连接和治理 Harness，具体任务仍应由 Agent 根据用户 Prompt、工作目录和工具环境自主完成。
