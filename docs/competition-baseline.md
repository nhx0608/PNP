# 多 Agent 引擎可替换架构实现：赛题基线

> 更新时间：2026-09-04  
> 本文用于沉淀当前已确认的赛题要求、评测规则与团队技术方向。内容基于赛题任务书、调测指南、网关接口规范以及当前已知评测用例整理。

## 1. 赛题目标

赛题要求基于 **Agent 网关 + Agent 引擎（Harness）** 的架构，构建一个支持多种 Agent 引擎快速替换的智能体系统。

任务书点名的两个同构范例是 **OpenClaw**（开源）与**内部 AI 应用员工助手 MyAgent**（内源），
后者正是第二套网关规范的出处。

核心角色：

- **Agent 网关**：面向业务，负责业务请求到 Agent 引擎的连接与映射，并承担会话管理、消息路由、权限控制、事件输出等职责。
- **Agent 引擎 / Harness**：面向智能执行能力，负责 LLM 调用、Agent Loop、工具调用以及实际任务执行。

赛题关注点不是实现某一类特定办公任务，而是：

1. 在保持 Agent 应用/网关架构稳定的前提下，能够替换不同的 Harness；
2. 至少接入两种不同 Agent 引擎；
3. 不同引擎通过同一套评测网关接口被调用；
4. 引擎切换后仍能完成真实 Windows 环境中的任务执行。

## 2. 背景与场景

赛题背景指出，Agent 网关 + Harness 已成为 Agent 应用的一种典型架构模式。

以群助手为例，网关需要把业务请求映射到底层某个具体 Session，使系统能够实现：

- 同一群会话连续；
- 不同群会话上下文隔离；
- 权限边界控制；
- 业务逻辑与底层 Agent 执行能力解耦。

业界 Harness 快速演进，因此系统需要降低接入新引擎的成本，而不是把上层业务架构与某一个 Agent 引擎绑定。

## 3. 已确认硬性要求

### 3.1 运行环境

- 操作系统：**Windows 10 / Windows 11**；
- 可以使用 Node.js、Python 或其他技术栈；
- 主模型限定使用内部部署模型资源：赛题组**提供测试环境的 appid 并协助申请资源**，也可使用其他内部部署模型；
  即鉴权可能是 appid 形式而非标准 API key，模型接入层要能容纳这种自定义鉴权头；
- 参赛代码需要由评测方在沙箱环境中部署、启动和执行。

### 3.2 多引擎要求

- 至少接入 **2 种不同的 Agent 引擎**；
- 引擎应为真实可运行的 Harness，而不是仅切换底层模型；
- **必须通过环境变量实现引擎切换**（任务书"重要提示"逐字要求）；
- 不要求同一进程运行期间动态热切换；
- 比赛会在不同轮次分别启动不同引擎进行评测。

任务书给出的环境变量示例：

```text
AGENT_ENGINE=opencode    # 或 pi、hermes 等
```

> **优先级**：环境变量是硬性要求，命令行参数只是通用网关规范附带的等价形式。
> 实现上以 `AGENT_ENGINE` 为准，`--engine` 作为可选覆盖；两者都提供时应明确优先级并在
> `INSTRUCTION.md` 中写清楚，避免评测方按环境变量启动却被命令行默认值覆盖。

```text
gateway --engine opencode --port 6217   # 可选，等价于 AGENT_ENGINE=opencode
```

### 3.3 网关要求

赛题提供了两套网关规范，**实现其中任意一套即可支撑评测**：

1. 通用 Agent 网关规范，默认端口 `6217`；
2. MyAgent 网关规范，默认端口 `3008`——MyAgent 即任务书背景中点名的**内部 AI 应用员工助手**，
   是赛题所说"真实业务系统"的原型，这解释了它的路径里为何保留 `/opencode/` 命名。

两套规范都要求覆盖以下核心能力：

- 创建任务对应的 Agent / Session；
- 指定工作目录；
- 发送用户 Prompt 并阻塞到本轮完整结束；
- SSE 推送 Agent 执行事件；
- 获取完整消息/工具调用轨迹；
- 中止当前任务；
- 删除 Agent / Session；
- 正确维护 `idle` / `busy` 状态。

**关于反问与权限请求：接口必须实现，只有策略可以简化。**

任务书"重要提示"原文：**"执行过程需要人工交互的，需要实现接口供裁判模型自动提交交互，否则将导致作品无法完成自动评测。"**

这意味着：
- `/question`、`/permission` 这两条链路（事件推送 + 查询 + 回复端点）**必须真实可用**，因为裁判模型要靠它们把交互自动提交回来；
- 可以简化的是**默认策略**（例如默认允许、默认不询问），而不是接口本身；
- 若某个 Harness 在无头模式下会静默把"待确认"变成拒绝（Goose、Gemini 系均有此行为），网关必须把它的原生请求归一化后自动应答，否则表现为任务莫名失败。

详细协议整理见 [`gateway-api-baseline.md`](./gateway-api-baseline.md)。

## 4. 可选不实现项

赛题明确降低了部分要求，这些能力不是初赛硬性条件：

- 跨引擎 Session / 上下文同步；
- 持久化存储，会话可以只存在内存；
- 多 Agent 机制——任务书给出了具体的简化路径：**"可以每个引擎内置一个默认 agent，会话基于该 agent 创建"**；
- 复杂的 Agent Team 或 Workflow 编排。

因此，"多引擎可替换"本身是核心，不需要为了满足基础要求先构建复杂多 Agent 平台。
每个引擎一个默认 agent 是被明确认可的实现形态，Session 直接建在这个默认 agent 上即可。

## 5. 评测机制

### 5.1 两阶段评测

客观评价采用：

1. **Rollout**：让被测 Agent 在受控 Windows 环境中执行任务并记录完整交互过程；
2. **Evaluation**：由 LLM-as-Judge 对执行结果进行评价。

### 5.2 分值构成

- 客观评价：**70%**；
- 方案、架构合理性：**20%**；
- 创新性：**5%**；
- 鲁棒性：**5%**。

### 5.3 多引擎计分方式

评测会对选手接入的每个引擎分别执行。

**同一个评测用例取所有参赛引擎中的最高分，所有用例得分之和构成该题客观得分。**

这意味着：

- 多个引擎可以具有不同能力特长；
- 不要求不同 Harness 的内部行为完全一致；
- 引擎数量增加可能提高任务覆盖率，但同时会增加部署和稳定性成本。

## 6. 当前已知评测任务覆盖面

目前已获得 10 条测试参数，覆盖：

- Word 文档润色与结构化内容提取；
- CSV / Excel 数据分析；
- PPT 内容编辑和生成；
- 文件系统递归删除；
- Word 表格转 Excel；
- Windows 即时通讯软件交互；
- 实时资讯检索与分析。

当前样例主要用于观察不同 Harness 在真实办公和 Windows 环境中的执行能力，并不改变本题的核心：**多 Agent 引擎接入与替换架构**。

详细用例见 [`evaluation-cases.md`](./evaluation-cases.md)。

## 7. 提交物要求

最终提交包：

```text
solution/
├── INSTRUCTION.md
└── code/
```

### `INSTRUCTION.md`

至少需要说明：

- 环境准备；
- 依赖安装；
- 编译 / 启动方式；
- 引擎切换方式；
- 调用和执行顺序；
- 执行完成判定；
- 结果交付件说明。

### `code/`

- 完整源码；
- 保持工程目录结构；
- 包含依赖和配置声明；
- 如有 SDD 等工程产物可一并提交。

自动评测不能依赖人工操作；若执行过程需要反问或权限确认，应通过接口使评测程序能够继续处理。

## 8. 调测要求

官方调测建议按以下顺序进行：

1. 验证 Windows 运行环境、模型服务和环境变量；
2. 单引擎运行简单任务；
3. 逐步测试不同难度用例；
4. 切换第二个引擎并执行相同任务；
5. 反复启动、切换，验证 Session 隔离和稳定性；
6. 验证 Rollout 轨迹与 Evaluation 流程；
7. 对全部用例执行回归，统计不同引擎得分并分析失败原因。

## 9. 当前团队技术方向

当前已确认采用：

> **自研 Agent 网关 / 多引擎架构，而不是基于 MyAgent 直接改造。**

目标是接入多个可下载安装、业界实际使用的 Agent Harness，并将“接入第三个、第四个引擎”的成本作为架构设计的重要评价指标。

当前讨论中的候选方向包括 OpenCode、Pi、Hermes、Goose、DeepSeek Harness 等；最终接入列表需要结合 Windows 原生可运行性、内部模型兼容性、Agent 执行效果和自动部署稳定性进一步验证。
