# 独立架构方案（设计过程存档）

这五份方案由五位独立架构师从互不相同的角度、基于同一份调研语料（[`../../research/`](../../research/README.md)）分别写成，彼此不可见。它们是最终架构的**输入**，不是结论；最终综合稿见 [`../architecture.md`](../architecture.md)。

保留它们的理由：最终架构的每个决策都能追溯到"哪些角度支持、哪些角度反对、为什么这样裁决"。

| 方案 | 角度 | 核心主张 |
| --- | --- | --- |
| [A](./proposal-A-protocol-first.md) | 协议与契约优先 | PNP 是一组可独立实现的契约而非一个网关程序；成败标准是外部工程师能否照规范独立写出第 5 个引擎的适配器 |
| [B](./proposal-B-gateway-core-first.md) | 评测规范与网关核心优先 | 从赛题北向契约倒推内部模型；重点在阻塞语义、轨迹归一化、状态机与 abort 传播 |
| [C](./proposal-C-orchestration-first.md) | 编排与元智能体优先 | 节点 = 引擎 + 能力 + 配置；评测路径是单节点工作流的退化形态，MVP 与愿景共用同一执行器 |
| [D](./proposal-D-platform-first.md) | 平台工程与 Windows 运维优先 | 评测方在干净 Windows 沙箱里一条命令能否确定性跑起来、跑得完、杀得干净、看得见 |
| [E](./proposal-E-pragmatic-competition.md) | 务实夺冠与反过度设计 | 3 人 4-6 周的边界；每处设计标注 MVP/v2/展望，且标注是承诺 |

方案间的主要分歧（由评审裁决后写入最终架构）：ACP 作为基线协议的定位、引擎数量与选型、编排层在 MVP 中的存在形态、是否引入持久化与可观测全家桶。
