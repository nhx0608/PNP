# 需求与交付范围

## 1. 依据与解释优先级

依据包括用户提供的《多 agent 引擎可替换架构实现—任务书》《调测指南》、两套网关接口规范，以及明确的项目要求。原始接口材料位于 [参考目录](../reference/README.md)。官方要求与项目选择分别标注；不得把方案自行增加的约束表述成赛题强制条件。

## 2. 赛题约束

| ID | 原始要求 | PNP 实现决策 |
|---|---|---|
| R01 | Windows 10/11 运行，提交源码及编译启动方式 | 原生 Windows；不要求 WSL、Docker、数据库服务 |
| R02 | 至少两种不同 Agent 引擎 | OpenCode、Pi 为必过引擎，两者都通过正式验收才可发布；Hermes 为可选第三引擎，有证据加分，无证据不阻断发布 |
| R03 | 必须能通过环境变量切换引擎 | `AGENT_ENGINE`；同时支持规范中的 `--engine`；二者冲突则启动报错 |
| R04 | 两套网关规范任选一套 | 完整实现通用 6217 规范；MyAgent 仅作为参考材料 |
| R05 | 主模型使用内部部署资源 | 每轮解析经过授权的内部模型配置，支持 API key、appid、自定义头及证书要求 |
| R06 | Rollout 完整执行记录；LLM-as-Judge 评价 | 消息、工具状态、停止原因和产物引用可追溯；不伪造执行成功 |
| R07 | 需要人工交互时必须提供自动提交接口 | 选择实现 Question/Permission 闭环；默认策略不覆盖组织权限拒绝 |
| R08 | 提交 `solution.zip`，包含 `INSTRUCTION.md` 和 `code/` | 发布脚本排除运行数据、凭据、测试账号和依赖缓存 |
| R09 | 单个用例对所有参赛引擎分别执行并取最高分 | 评测路径每次只启动一个选定引擎，不在网关内双跑取优 |

评分权重：客观 70%；架构合理性 20%；创新性 5%；鲁棒性 5%。初赛截止后统一评测一次，不假设评测方会人工修复安装问题。

题目允许不实现跨引擎会话同步、持久化及多 Agent。PNP 的本地持久化是项目明确要求，不是赛题硬性条件。Question/Permission 在接口附件中有可选说明；当系统产生相应交互时，回传必须真实可用。

## 3. 项目约束

| ID | 项目要求 | 约束 |
|---|---|---|
| P01 | 自研稳定网关，连接可下载 Harness | 不能把仅切换模型或工具 CLI 计为接入不同引擎 |
| P02 | Session 本地持久化 | SQLite 保存会话、Run、消息和绑定；内存不能是唯一事实源 |
| P03 | 三人开发，A/B 同时开发 | 公共框架独立交付；A/B 不互相等待对方引擎代码 |
| P04 | C 对接内网 | 模型、工具、权限通过 IntegrationProvider 解耦；正式联合验证在内网 |
| P05 | 轻量并具备 DFX | 单网关、单执行槽加有界队列、本地存储、有限资源；不引入外部基础设施 |
| P06 | 可供没有会话上下文的 Agent 执行 | 文档、接口、任务、测试和分工在仓库内自足 |

## 4. 必须实现的能力

必须项包括：北向 API、持久化 Session/Run/Message、原生会话绑定、启动选择引擎、工作目录、模型绑定、SSE、取消与停止核验、错误归一化、有限超时、交互闭环、进程归属、能力包投影、内网工具和授权、自动部署说明、真实引擎与内网测试。

复杂但不可删除的项是：跨进程取消、崩溃后的资源核验、内部模型工具调用兼容、真实权限传递、消息终态与持久化一致性。这些直接影响评测正确性与外部副作用安全。

## 5. 架构亮点及闭环

| 亮点 | 实施范围 | 必须提供的证据 |
|---|---|---|
| 一套 ACP Driver 支持多个 Harness | A 负责 OpenCode 的通道差异和配置；Hermes 可选 | 同一公共 Driver、不同 Pack 均通过契约测试 |
| 非 ACP 引擎接入 | B 负责 Pi RPC | 不修改 Gateway/Core 接入并完成真实任务 |
| 通道级能力描述 | 引擎版本 × 通道 × 模型 × 资产配置 | 区分声明、探测、实测，不用全为 true 的能力矩阵 |
| 原生能力保留 | 技能/工具注入以及至少一种可验证的原生扩展 | 配置输入、引擎确认、执行轨迹和结果验证 |
| 引擎无关的能力包 | 三个能力包由配置启用，投影到每个必过引擎 | 同一包在两个引擎上都有投影事件与任务产物 |
| 可恢复会话与诚实终态 | 本地状态 + 原生恢复 + 停止证据 | 重启后历史不丢；未核验停止只阻断该会话；不重放任务 |
| 共用开发契约 | A/B/C 同一框架和验收套件 | 独立开发分支可组合运行，公共接口无私有分叉 |

不以堆叠模块数量、编写泛化平台或增加未经测试的引擎数量作为亮点。

## 6. V2 范围

跨引擎无损会话迁移、运行中热切换、外层 Dynamic Workflow/Agent Team/Room、自动引擎路由、统一自进化、跨引擎记忆同步、分布式多副本、HTTP/SDK 通道的完整独立实现属于 V2。V1 允许引擎在自己的执行器内部使用这些原生能力，但不承诺已经实现对应的网关编排语义。

## 7. 已知评测覆盖

10 个参数样例涉及 Word 精确改写、CSV 客户分析、库存分析、PPT 编辑/生成、即时通讯、递归文件删除、DOCX 表格转 XLSX、最新资讯检索。它们验证通用系统和 Harness 的能力，不是网关分支条件。不得使用 `task_id/category/difficulty` 硬编码答案、工具选择或产物。

能力注入是一等交付物。三个能力包 `office`、`windows-desktop`、`web-search` 各有所有者、目录与验收项，定义见[契约第 10 节](contracts.md#10-能力包)；它们覆盖已知样例的九条，与引擎接入同等优先。

工具来源优先级：已有 Harness 能力、已授权员工助手 CLI、能力包内的 MCP/Skills、确实缺失的最小补充。Python、Office 组件与视觉模型属于各能力包的运行时依赖，由探测规则在打开通道时判定；不把它们变成 Gateway 本身的无条件依赖。
